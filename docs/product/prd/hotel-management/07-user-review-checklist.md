## A. 사용자가 직접 확정한 핵심

- [x] 호텔은 위아히어 법인 아래 내부 지점이다.
- [x] 초기 사용자는 사내 임직원·호텔 소유주·하우스키핑이며 거래처 임직원은 확장 MVP다.
- [x] 하우스키핑은 사람별 독립 사용자유형이고 공용계정이 아니다.
- [x] 호텔 소유주는 호텔당 1명, 계정당 호텔 1곳이다.
- [x] 다른 소유주로 교체할 때 사람 identity는 재사용하지 않고 연결만 교체한다.
- [x] 객실·시설물점검, 하자보수·방문일정, 일매출·운영이슈·소유주 문의를 초기 MVP에 포함한다.
- [x] PMS·채널매니저·OTA와 객실 판매·투숙·공실·청소·보수중 운영상태 흐름은 제품범위에서 제외한다.
- [x] 파일은 비공개이며 조회·다운로드 권한은 관리자 화면에서 설정한다.
- [x] 사용자는 파일마다 승인요청 없이 설정된 권한으로 즉시 사용한다.

### 최신 승인정책에 따른 대체·추가

- [x] 회사 공통 객실유형 대신 호텔별 독립 객실유형을 사용한다.
- [x] 객실 기준정보의 활성·사용중지·삭제는 신규 업무대상 포함 여부만 뜻한다.
- [x] 객실점검과 시설물점검은 대상 기준정보만 분리하고 공통 inspection·process·권한·사진·감사·보수 기반을 재사용한다.
- [x] 정기·수시점검은 특정 완료책임자에게 고정하지 않고 호텔 지점 공용업무로 생성하며 항목별 실제 수행자를 기록한다.
- [x] 결과는 정상·주의·이상이고 주의 설명, 이상 설명·사진 1~5장을 필수로 한다.
- [x] 설정형 검토 process revision·단계·전이·검토자·대리·기한·지연·완료조건을 DB 정본으로 사용한다.
- [x] 역할명 하드코딩 없이 회사/호텔 역할과 사용자 추가·회수 예외를 계산하고 개인 회수가 우선한다.
- [x] 활성 최고관리자는 항상 정확히 두 명이며 교체를 한 transaction으로 처리한다.
- [x] 점검결과만으로 운영이슈·보수 건을 자동생성하지 않고 프로세스 판단으로 별도 보수 건을 만든다.
- [x] 보수대상은 객실·공용공간·시설물이며 보수 건 하나에 대상 하나만 연결한다.
- [x] 자체 월간·주간 달력과 PostgreSQL 정본 기반 점검·보수 일정 조회를 사용한다.
- [x] 외부 달력 provider·OAuth·외부 event 동기화는 구현하거나 노출하지 않는다.
- [x] 관리번호·QR·바코드·자산정보·비용·견적·청구·외부업체 포털은 초기 MVP에서 제외한다.

## C. 사용자 명시예외
